## DEFECT-001 — жизненный цикл image reservation нарушен при retry и cancel

Приоритет: **P0**, OPEN. Кейсы: `TC-USG-014`, `TC-USG-015`, `TC-USG-016`.
Воспроизводится с реальными `UsageService`, `PublishingService` и PostgreSQL; провайдеры и Telegram — mocks.

### A. Ручной retry после release

1. Создать image Post и READY Publication с резервом IMAGE_GENERATION=1.
2. Установить максимум попыток 1; первая генерация изображения возвращает retryable network error.
3. Убедиться: FAILED, reserved=0, committed=0.
4. Через HTTP вызвать `POST /api/v1/publications/:id/retry`: API отвечает 202.
5. Повторить publisher; генератор на этот раз успешен.

Ожидание: законно восстановленный резерв, PUBLISHED, одно committed IMAGE_GENERATION.
Факт: **FAILED**, `errorCode=TELEGRAM_API_UNAVAILABLE`, фото не отправлено, reserved=0/committed=0.
Ручной retry сбрасывает статус, но не восстанавливает освобождённый резерв; следующий commit quota не проходит.
Дополнительно ошибка учёта маскируется как недоступность Telegram.

### B. Ошибка изображения после уже применённого commit

1. Создать image reservation; сгенерировать файл; commit quota успешен.
2. Telegram возвращает 429; статус RETRY_WAIT; committed=1/reserved=0.
3. Наступить времени второй попытки; image provider возвращает terminal error.

Ожидание: безопасный FAILED без повторного release уже использованной квоты.
Факт: исключение «There is not enough reserved usage for this operation», публикация остаётся **PUBLISHING**,
committed=1/reserved=0; исходный errorCode остаётся TELEGRAM_RATE_LIMIT.
Транзакция terminal failure откатывается из-за попытки повторного освобождения отсутствующего резерва.

### C. Cancel после image commit

1. Повторить первую попытку из B до RETRY_WAIT.
2. Вызвать `POST /api/v1/publications/:id/cancel`.

Ожидание: CANCELLED, committed остаётся 1, повторный release не выполняется.
Факт: **HTTP 409**, состояние остаётся RETRY_WAIT; корректная пользовательская отмена не проходит.

Код для расследования: `src/publishing/publishing.service.ts` — `retry`, `publishWithImage`, `handleError`,
`cancel`, `fail`; `src/subscriptions/usage.service.ts` — reserve/commit/release.
Нужна согласованная модель резерва/расхода по publication и исходному периоду, а не простое подавление ошибки.
Не исправлено в этом прогоне. После исправления повторить все три кейса и связанные month-boundary/retry сценарии.

<a id="defect-002"></a>

## DEFECT-002 — FIRE_ONCE игнорирует превышение grace-периода

Приоритет: **P0**, OPEN. Кейс: `TC-SCH-017`.

1. Создать ONCE schedule, `misfirePolicy=FIRE_ONCE`, `misfireGraceSeconds=86400`.
2. Установить `runAt` и `nextRunAt` на 25 часов до тестового `now`.
3. Другой schedule fixture поставить на PAUSED; вызвать `SchedulesService.materializeDue(now)`.

Ожидание из scheduling contract: **SKIPPED**, нет AI reservation/outbox.
Факт: **PENDING**, создан один generation outbox event и резерв платной работы.
В материализации ONCE проверка outside-grace включена только для policy SKIP.

Код: `src/schedules/schedules.service.ts`, одноразовая ветка materialize.
Риск: публикация устаревшего поста и расход квоты после длительного простоя.
Не исправлено. Retest: FIRE_ONCE внутри/на/вне grace; SKIP; restart/catch-up; отсутствие новых jobs для SKIPPED.

<a id="defect-003"></a>

## DEFECT-003 — PATCH только заголовка поста возвращает 500

Приоритет: **P1**, OPEN. Кейсы: `TC-BND-026`, `TC-BND-027`, `TC-BND-028`, `TC-BND-029`.

1. Создать ACTIVE Post с валидными prompt, channel и текущей версией.
2. От владельца подписать `PATCH /api/v1/posts/:id` с актуальным `If-Match`.
3. Передать только `title` длиной 0, 1, 254 или 255 ASCII символов.

Ожидание: допустимый частичный PATCH, неуказанные поля сохранены; пустой optional title нормализуется в null.
Факт: **HTTP 500** для каждого PATCH-варианта. Соответствующие POST-варианты проходят.
Вероятная причина подтверждается кодом: DTO после transform содержит undefined-поля;
`{ ...current, ...dto }` перекрывает исходный prompt значением undefined, затем `normalized` вызывает `.trim()`.

Код: `src/posts/posts.service.ts`, `update` и `normalized`.
Не исправлено. Retest должен включать все одиночные optional PATCH-поля, omit/null и сохранность остальных полей.

## Исправления только тестового окружения

Первый integration запуск дал 25 PASS / 2 FAIL. Причина: локальный `.env` выбирал реальную image-модель,
а mock catalogue ожидал `gpt-image`. Эти два падения не засчитаны как runtime-дефекты приложения.
`test/setup-env.ts` теперь явно задаёт фиктивные provider/Telegram keys, модели и параметры.
Повторный integration запуск: **27/27 PASS**. Это также предотвращает наследование настоящего API key из `.env`.

При написании harness исправлены невалидные fixture enum/обязательные поля и неверная проверка допустимой
нормализации пустых title/description в null. Результаты неработавшего harness не перенесены в каталог.
`TC-SCH-001` исправлен в каталоге: фактический API enum — `ONCE`, а не `ONE_TIME`; ожидание misfire не менялось.

## Воспроизведение

Требуется Node 24.15+, npm согласно package.json; **свои отдельные** loopback PostgreSQL/Redis.
Примеры URL ниже относятся только к disposable test-сервисам и не создают их автоматически.

```bash
export AUTOBOT_TEST_DATABASE_URL='postgresql://autobot@127.0.0.1:55433/autobot_acceptance_test?schema=public'
export AUTOBOT_TEST_REDIS_URL='redis://127.0.0.1:56381/15'
DATABASE_URL="$AUTOBOT_TEST_DATABASE_URL" npm run prisma:migrate:deploy
npm test
npm run test:integration
npm run test:acceptance
```

Acceptance требует явных URL, loopback-host и имени БД с суффиксом `_test`.
Перед каждым кейсом fixture очищает **все данные этой тестовой БД**. Не запускать параллельно с другой
suite в той же БД. Автоматические dispatcher/scheduler отключены; queue workers имеют отдельный prefix.
Сейчас `test:acceptance` намеренно возвращает ненулевой exit code: ожидаемые корректные результаты
проверяются обычными assertions, найденные дефекты не спрятаны через skip/expected-failure.
Default CI unit/integration suites от этих новых падающих acceptance-кейсов не зависят; typecheck/lint их проверяют.
