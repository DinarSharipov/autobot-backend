## Новые находки

<a id="defect-004"></a>

### DEFECT-004 — часть конкурентных onboarding завершается 500

Кейс **TC-USR-003 (P0 по каталогу)**. На чистых fixtures отправить 20 одновременно подписанных
`POST /api/v1/internal/telegram-users/resolve` с одним новым Telegram ID и разными nonce.
Ожидание: все ответы 200 с одним userId; одна учётная запись.
В итоговом прогоне **14 ответов 200 и 6 ответов 500**. Ошибка воспроизводилась
в нескольких прогонах; количество 500 меняется. PostgreSQL сохранил **одного нового User
и один TelegramAccount** (общее число пользователей 3, включая A/B). Дубли не обнаружены.

В `IdentityService.withIdentityRetry` есть ограниченный retry сериализуемых транзакций.
Недостаточность retry под конкуренцией — гипотеза по коду; точная причина 500 требует диагностики.
Нельзя считать, что защита от дублей означает успешный onboarding всех клиентов.

<a id="defect-005"></a>

### DEFECT-005 — повторный onboarding DELETED-пользователя возвращает 500

Кейс **TC-USR-008 (P0 по каталогу)**. Пометить своего fixture-пользователя DELETED,
выполнить подписанные GET `/me`, POST `/topics`, POST internal `/resolve`.
Первые два запроса корректно возвращают 401. Resolve возвращает **500** вместо контролируемого
отказа. Состояние в БД остаётся DELETED, новых пользователей нет; восстановление прав не обнаружено.
По коду `resolveBotUser` возвращает существующего удалённого пользователя, а `toUserView`
выбрасывает ошибку при DELETED. Нужен доменный отказ до преобразования ответа.

Для BLOCKED-пользователя защищённые команды также возвращают 401; onboarding возвращает 200
с явным статусом BLOCKED, не реактивируя пользователя. **TC-USR-007 PASS** по правилу каталога:
отказ защищённого доступа и отсутствие реактивации. Это не требование отклонять сам resolve.

<a id="contract-006"></a>

### CONTRACT-006 — AuthIdentity не создаётся при первом входе через бота

Кейс **TC-USR-001 (P0 по каталогу)** остаётся FAIL относительно записанного oracle:
он требует User + TelegramAccount + AuthIdentity. Реальный ответ 200 создаёт User и TelegramAccount,
но **AuthIdentity count = 0**. В текущем коде AuthIdentity появляется в OIDC flow, тогда как bot flow
опирается на TelegramAccount. Повторный onboarding и конфликтующие OIDC-привязки проверены отдельно.

Это **расхождение требования каталога и модели реализации**, а не доказанный обход авторизации.
До изменения runtime нужно определить, требуется ли AuthIdentity уже при bot onboarding,
или oracle должен различать TelegramAccount и OIDC identity. Ожидание теста не изменялось
ради зелёного результата; активация Web Admin не выполнялась.

## Уточнения harness

- Ротация ключа проверена после удаления previous-пары из конфигурации **и process env**.
  Первоначальная попытка изменить только ConfigService возвращала значение из env;
  это был дефект тестовой подготовки, не runtime-уязвимость.
- Второй канал для shared-topic fixture теперь явно ACTIVE, как требует контракт.
- Отказ при чужой теме проверяет установленный доменный код TOPIC_NOT_ACTIVE/422;
  каталог требует отказ, а не конкретно 403/404.
- Для неизвестного маршрута установленный контракт — NOT_FOUND/404.
- Clock skew 60 секунд и TTL 300 секунд заданы явно. Проверены обе границы ±60 и ±61.
- При первом старте native Redis неверная locale остановила процесс до исполнения тестов.
  Redis перезапущен с LC_ALL=C; первоначальный неуспешный setup не учитывается как результат кейсов.

## Повторение

На новых disposable loopback PostgreSQL/Redis применить миграции и выполнить:

```sh
AUTOBOT_TEST_DATABASE_URL=postgresql://autobot@127.0.0.1:55433/autobot_acceptance_test \
AUTOBOT_TEST_REDIS_URL=redis://127.0.0.1:56381/15 \
npm run test:acceptance
```

Требуется Node >=24.15.0. Тесты отказываются работать без явных test URL,
с не-loopback host или именем БД без суффикса `_test`. До устранения дефектов suite возвращает 1.
