Дата составления: **16 октября 2026**. Область: backend этого репозитория, интеграция Telegram-бота,
GPTunnel и эксплуатация. **667 тест-кейсов в 31 разделах**, включая отдельные строки для

Это практический регрессионный каталог по текущему коду и утверждённому плану. Все возможные сочетания
входов бесконечны: для них ниже заданы классы эквивалентности, граничные проверки и правила расширения
матриц. Новая функция, найденный дефект или изменённое правило добавляют новый стабильный ID.

По каталогу выполнено **168 кейсов: 157 PASS, 11 FAIL, 499 NOT_RUN**. В новой партии

## Как проходить и фиксировать результат

- У каждого кейса независимый ID `TC-РАЗДЕЛ-NNN`; при добавлении кейсов существующие ID не перенумеровывать.
- Все кейсы первоначально имеют **NOT_RUN**. Этот файл не означает, что они уже выполнены.
  Наличие unit/integration теста и прошлый успешный smoke не заменяют доказательство текущего прогона.
- После выполнения заменить статус на `PASS`, `FAIL`, `BLOCKED_FEATURE`, `BLOCKED_ENV`, `BLOCKED_SPEC`,
  `DEFERRED` или `N/A`. В последнем столбце указать run ID и ссылку на доказательство/дефект.
- `PASS`: проверены все ожидаемые эффекты, включая PostgreSQL, ledger, очередь и Telegram там, где требуется.
  Только HTTP 200/202 или успешный выход job недостаточны.
- `FAIL`: фактический результат нарушает однозначный контракт. Не заменять обнаруженный баг на PASS,
  исправляя ожидаемый результат под текущий код. Создать дефект и после исправления повторить кейс.
- `BLOCKED_FEATURE`: функция/механизм ещё не реализован. `BLOCKED_ENV`: нет стенда, прав, аккаунта,
  бюджета или доступа к каналу. `BLOCKED_SPEC`: нет единого утверждённого ожидаемого поведения.
- `DEFERRED`: продуктовая область отложена. `N/A` требует явной причины; не использовать для скрытия дефекта.
- Варианты, перечисленные в одной строке (например, 401/402 или несколько полей), выполняются отдельно;
  PASS допустим только если прошёл каждый вариант. Фактический ответ и наблюдение записывать по каждому.
- Для расширения выбрать комбинации из матриц в конце; сохранять seed и конкретные значения.

Приоритеты: **P0** — обязательный выпускной блокер (безопасность, потеря данных, дубль/неверная отправка,
платный расход); **P1** — основной регресс; **P2** — дополнительные проверки по мере расширения продукта.
Сейчас P0: **416**, P1: **251**. Приоритет не означает разрешение на опасный production-тест.

Области: `ACTIVE` — текущий backend/бот; `TARGET` — приёмка проектных требований/уточнение контракта;
`DEFERRED` — будущий браузерный клиент. Активных: **630**, целевых/контрактных: **13**,
отложенных: **24**. В WEB-001 проверка безопасного отключённого OIDC актуальна уже сейчас;
она не требует включения Web Admin.

Режимы: `AUTO` — unit/contract/integration с fixtures; `STAGE` — изолированная БД/Redis и fault injection;
`LIVE` — реальные GPTunnel/Telegram с контролируемым бюджетом; `CLIENT` — отдельный репозиторий бота;
`REVIEW` — проверка и согласование контракта; `FUTURE` — только после возобновления браузерной части.

## Предусловия всего прогона

1. Зафиксировать commit SHA backend и бота, image digest, Node/PostgreSQL/Redis, дату и timezone стенда.
   Не считать локально изменённый файл доказательством версии, запущенной на сервере.
2. Подготовить A и B — разных пользователей с независимыми Telegram identity; C — неактивного пользователя.
   Отдельные fixtures: free, действующая pro, trial, истёкшая/будущая подписка, последняя единица квоты.
3. Подготовить публичный и приватный **тестовые** каналы; канал без прав бота; группу и супергруппу.
   Каждый LIVE-кейс явно привязан к разрешённому каналу и пользователю. Не использовать чужой production ID.
4. Для доменных команд использовать реальную HMAC/REST-границу; для невозможных промежуточных состояний —
   fixtures/harness только на изолированном стенде. Нет публичного admin API изменения плана/статуса:
   fixture нельзя выдавать за доступную пользовательскую функцию.
5. Перед платными сценариями проверить действующий ключ, authenticated каталоги, баланс и бюджет.
   Не записывать ключи, raw HMAC, cookie secret, prompts/transcripts, image bytes/URL/path в доказательства.
   Итоговый пост, безопасные IDs, normalised error codes и агрегаты квот допустимы.
6. Отключение зависимостей, Redis flush, SIGKILL, ENOSPC, восстановление БД, ротацию ключей, изменение часов
   и нагрузку выполнять **только на изолированном STAGE**. Этот каталог не является разрешением разрушать production.
7. Браузерная часть по текущему `docs/AGENTS.md` отложена. Её тесты не требуют активации OIDC в production.
   Контрактные auth-тесты можно выполнять локально на mocks.
8. Для каждого теста зафиксировать исходные counters, resource versions и число сообщений; после — сверить
   состояние и удалить/архивировать только собственные тестовые ресурсы, остановить тестовые schedules.
   Уже отправленные сообщения не удалять без согласованной cleanup-политики. Секреты не коммитить.

## Порядок прохождения

1. **Подготовка и smoke:** ENV, HTTP, OBS; доступность health, правильный SHA и конфигурация моделей.
2. **Основа и безопасность:** HMAC, USR, OWN, CHN, TOP, SUB, USG, IDM, BND, PAGE.
3. **Функциональный pipeline:** PST, TXT, IMG, TMP, MOD, PUB, E2E; сначала mocks, затем LIVE.
4. **Время и устойчивость:** SCH, RRU, TZ, STM, QUE; затем STAGE recovery.
5. **Релизная готовность:** SEC, OPS, PERF, BOT. SPEC закрывается до приёмки зависимых случаев.
6. **Будущий Web Admin:** WEB после отдельного продуктового решения; WEB-001 выполнить уже в текущем smoke.

Сначала пройти все применимые P0. Не выполнять массовую LIVE-матрицу за реальные деньги:
протокол и негативные ответы проверяются на mocks; реальным провайдерам достаточно выбранных репрезентативных
успешных/доступных негативных проверок. При критическом дефекте остановить зависимые кейсы и отметить блокировку.

## Справочные лимиты и проверки oracle

Снимок конфигурации из `src/subscriptions/entitlement.types.ts`, а не обещание неизменных тарифов:

| Показатель                    |      free |       pro |
| ----------------------------- | --------: | --------: |
| Каналы                        |         1 |        10 |
| Темы                          |         3 |        50 |
| TEXT_GENERATION/UTC-месяц     |        30 |      1000 |
| IMAGE_GENERATION/UTC-месяц    |         0 |       100 |
| MODERATION_REVISION/UTC-месяц |         0 |       250 |
| Изображения/модерация         | запрещены | разрешены |

При изменении tariff definitions сначала обновить fixtures и этот снимок; все boundary-кейсы должны
оставаться относительно текущих лимитов. Баланс провайдера и продуктовые usage counters — разные величины.

- Генерация final text: 4096 UTF-16 code units для text-only, 1024 для image caption.
- Размеры API-строк из DTO: имя/заголовок 255; description 2000; prompt/template 20000; feedback 4000.
- Idempotency-Key: 16..128 printable ASCII. If-Match: quoted positive safe integer, например `"1"`.
- Страничный default обычно 25; max=100 там, где объявлен. Отсутствующий предел publications — отдельный SPEC.
- HTTP-коды успешных команд проверять по текущему controller/OpenAPI: create обычно 201, async-команда 202,
  delete 204, read 200; не подменять это глобальным правилом для всех POST.
- После success: не более одной immutable финальной версии для одной попытки генерации; одна выбранная версия
  на occurrence; один ожидаемый Telegram message; корректный usage ledger; временных файлов нет.
- После отказа: ожидаемый normalised code, отсутствие запрещённых side effects, нет вечного reservation,
  GENERATING/PUBLISHING или неограниченного retry. Для ambiguous delivery не обещать exactly-once.

успешный случай, невалидный ввод, отсутствие авторизации (кроме публичных), ownership где применим,
допустимый и недопустимый lifecycle, повтор/idempotency и ошибка зависимости. Отсутствие отдельного
ID для комбинации не делает её автоматически PASS: добавить параметризованный sub-run или новый ID.

## Дополнительные матрицы расширения

Каждая выбранная комбинация получает запись `RUN-ID / TC-ID / variant`. Невалидные комбинации
не запускать как LIVE-публикации: фиксировать ожидаемый отказ на стенде.

| Измерение      | Набор значений                                                                                                                |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Клиент         | подписанный бот/API; будущий browser mock; неавторизованный клиент                                                            |
| Пользователь   | владелец; другой владелец; новый; inactive; deleted                                                                           |
| План           | free; pro; trial; future; expired; cancelled; past_due; unlimited fixture                                                     |
| Квота          | 0; limit−1; limit; limit+1; reserved; committed; released; граница месяца                                                     |
| Режим          | AUTO; MODERATION                                                                                                              |
| Медиа          | текст; PNG; JPEG; WebP; пустой; повреждённый; слишком большой                                                                 |
| Время          | immediate; one-time; daily; weekly; monthly; DST gap/overlap; misfire                                                         |
| Сущность       | active; archived; paused; terminal; все PublicationStatus из STM                                                              |
| Конкурентность | один запрос; последовательный дубль; 2; 20; 100 параллельных                                                                  |
| Зависимость    | healthy; slow; timeout; reset; 4xx; 429; 5xx; недоступна; потеря состояния                                                    |
| Момент сбоя    | до claim; после reservation; после DB commit; после enqueue; после provider response; во время upload; после Telegram success |
| Развёртывание  | один API; несколько workers; graceful restart; hard kill; rollout; rollback; restore                                          |
| Строки         | ASCII; кириллица; emoji; combining characters; RTL; переносы; control chars; пустые; null; границы DTO                        |

Минимум — все указанные значения по одному и **pairwise** для независимых измерений.
Полный cross-product обязателен для критичных связок: ownership×mutation; квота×конкурентность;
publication state×command; image retry×quota commit/release; месяц×reservation; DST×recurrence;
crash window×external side effect. Остальные комбинации выбирать по риску и документировать exclusions.

Property-based/fuzz дополнение (не заменяет детерминированные кейсы):

- Генерировать корректные и некорректные raw HTTP/HMAC bodies; хранить seed без секретов.
- Генерировать последовательности create/edit/archive/publish/approve/revise/cancel/retry: сохраняются
  ownership, unique occurrence, неизменяемость версий, неотрицательные квоты и terminal invariants.
- Генерировать RRULE в поддержанном subset; сравнивать с независимым эталоном и утверждёнными исключениями.
- Проверять повторяемость digest при перестановке JSON keys и канонизацию query при эквивалентных URL.
- Генерировать stream chunks разного размера для bounded download, включая разрыв после каждого chunk.
- Воспроизводить каждый найденный counterexample отдельным стабильным regression ID.

## Что не включать в текущую приёмку MVP

Telegram Mini App, email/password, дополнительные identity providers, платёжный эквайринг/checkout,
S3/MinIO, image preview до одобрения, video/audio/documents/media groups, рекламные рассылки и произвольные
частоты RRULE не заявлены текущим MVP. Их отсутствие не считать дефектом. При добавлении требований
создать новые разделы, а не автоматически активировать отложенные возможности.
Web Admin отложен отдельно: его отсутствие не мешает приёмке bot-only, но уже существующие auth boundaries
не должны быть сломаны.

## Условия завершения приёмки

- У каждого применимого кейса есть статус и доказательство; NOT_RUN не трактуется как успешный результат.
- Все применимые P0 проходят; нет открытых дефектов безопасности, потери данных, неверного получателя,
  дублей внешних side effects или ошибочного расхода квот.
- Зависимые от нереализованных функций случаи явно BLOCKED_FEATURE и входят в остаток плана;
  нельзя объявлять полную production readiness с непроверенным restore/recovery.
- SPEC-решения задокументированы, ожидаемые результаты синхронизированы с API/архитектурой.
- P1 failures имеют решение и владельца; исключения приёмки перечислены явно.
- LIVE прогон выполнен в разрешённых каналах; секреты и provider payloads не попали в отчёт.
- Test cleanup завершён; незавершённые/повторяющиеся тестовые публикации не оставлены активными.
